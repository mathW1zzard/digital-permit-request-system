## Environment comparison

Values are as collected from the running systems in `evidence/week16/E1-environment-comparison/01-settings.txt`.

| Setting | Development | Staging | Why it differs |
| --- | --- | --- | --- |
| Purpose | One developer, fast edits | Rehearse a real deployment | – |
| Code | Working copy, edited live | Release folder exported with `git archive` from one commit, `composer install --no-dev` | Staging runs exactly one known commit |
| `APP_ENV` / `APP_DEBUG` | `local` / **true** | `staging` / **false** | Closes F1: no debug pages |
| Log level | debug | warning | Less noise; no request data in logs |

| Web server | `php artisan serve` (one request at a time) + Node TLS proxy on 8443 | nginx with TLS on 8444, 4 `php-cgi` workers (ports 9101–9104) under a restart loop | Concurrency (W2) |
| Web app origin | `http://localhost:5000` (Flutter dev server) → API on 8443 (CORS) | Same HTTPS origin for the web app and `/api` | No cross-origin calls in staging |

| Gateway | `https://127.0.0.1:9443` (Node proxy) | `https://127.0.0.1:9444` (nginx); same mock and keys | Mock only (limitation) |
| Notification batch | 50 a minute | 200 a minute | S2 follow-up |
| Scheduler | `php artisan schedule:work` in a terminal | the same, inside `run.sh`'s restart loop; restarted on deploy (S3) | – |
| Readiness | `/api/health` | `/api/health`, rate-limited in nginx | – |
| Backups | none | `backup.sh` before every deploy (`mysqldump --single-transaction`) | Rollback |

**What this comparison found.** Two defects showed up only because staging differs from development:
- **S2:** an absolute path in `.env` broke notification dispatch.
- **S1:** keep-alive to `php-cgi` stalled requests.

Neither can happen in development, and no test before Week 16 could have caught them.

## How a release is deployed

`deploy/staging/deploy.sh <git-ref> [--skip-web]`. Every step is written to `shared/logs/ops.log`.

1. **Back up the database** (`backup.sh pre-deploy-<sha>`).
2. **Export the commit** into `releases/<time>-<sha>/` with `git archive`. Uncommitted changes can never reach staging.
3. **Install the backend:** `composer install --no-dev --optimize-autoloader`. `storage/` is a junction to `shared/storage`, and `shared/.env` is copied in.
4. **Build the web app:** a Flutter Web release build for `https://localhost:8444/api`, or the current build is reused with `--skip-web`.
5. **Prepare Laravel:** `php artisan migrate --force`, `config:cache`, `route:cache`.
6. **Switch:** point the `current` junction at the new release. Record the previous release, then restart the workers and the scheduler.
7. **Gate:** wait for `/api/health` 200. If it doesn't come, the script stops and says to run `rollback.sh`.

**Measured times:**

| Deploy | Total | Composer | Flutter build |
| --- | --- | --- | --- |
| Full | 5 min 22 s – 5 min 35 s | about 3.5 min | about 1.5 min |
| `--skip-web` | 3 min 37 s – 4 min 15 s | about 3.3 min | – |

The switch itself (step 6) takes about 12 s. Users see no downtime until then, and only the workers' restart after it.

## Deployment checklist

Run through this for every staging (and, later, production) release.

**Before**
- [ ] The commit is pushed and tagged. PHPUnit, the Flutter tests and analyze pass on it.
- [ ] Migrations in the release are backward compatible with the previous release: they add, never drop or rename. If not, plan a database restore as the rollback, and accept the loss of writes since the backup.
- [ ] Any new setting is in `.env.staging.example`, and its value is in `shared/.env`.
- [ ] Nothing secret is in the commit (secret scan).
- [ ] Note the current release from `shared/run/current-release` and the time.

**Deploy**
- [ ] `deploy/staging/deploy.sh <tag>` finishes with "health check 200".
- [ ] `ops.log` shows the backup file name and size.

**After (within 5 minutes)**
- [ ] `/api/health` shows `ready`, or `degraded` only for a reason you know (for example a backlog that is draining).
- [ ] `scheduler_dispatch` and `scheduler_automation` show `ok`. They prove the background jobs run the new code (S3).
- [ ] No new `exception.unhandled` in `permit.jsonl`.
- [ ] Smoke run: `perf/models/smoke.json`, 15 s, 0 errors.
- [ ] Sign in to the web app once, and open one permit.

**If any "after" check fails:** follow `34-rollback-and-recovery.md`.

## Not covered by these scripts

- **A real host:** a public name, a certificate from a public authority, and a firewall. Staging used the local development CA.
- **Linux deployment:** PHP-FPM and systemd units. The Windows scripts are specific to this laptop.
- **Zero downtime:** the workers restart for about 2 seconds during each switch.
- **Off-machine backups:** they stay in `shared/backups` on the same disk.
