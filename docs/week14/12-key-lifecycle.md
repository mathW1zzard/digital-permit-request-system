# Week 14 – Key and secret lifecycle plan

| Secret | Purpose | Generated by | Stored in | Who can read it | Rotation | If exposed |
| --- | --- | --- | --- | --- | --- | --- |
| `APP_KEY` | Encrypts permit details and comments; signs Laravel data | `php artisan key:generate` | `backend/.env` | Server operator | Laravel's `APP_PREVIOUS_KEYS` lets old data still decrypt while new data uses the new key | Generate a new key, put the old one in `APP_PREVIOUS_KEYS`, re-save records, then remove the old key |
| `GATEWAY_PAYLOAD_KEY` (id `k1`) | Seals the gateway recipient | `php artisan gateway:key` | `backend/.env`; receiver gets it as `GATEWAY_PAYLOAD_KEYS` | Server operator, gateway operator | New id `k2`: add `k2` to the receiver first, then switch the sender, then remove `k1` after the 5-minute window | Remove the key id from the receiver at once (messages fail safely to manual handling), issue a new key |
| `GATEWAY_API_KEY` | Bearer key the gateway checks | Random text | `backend/.env`, gateway environment | Both operators | Change both sides together | Change both sides; requeue failed notifications |
| TLS private key (`certs/localhost-key.pem`) | HTTPS for the proxy | `php tls-proxy/make-dev-certs.php` | `certs/` (git-ignored) | Developer | Certificate valid 397 days; delete `certs/` and regenerate | Regenerate; the CA private key is never saved, so nothing else can be signed with it |
| `DEMO_PASSWORD` | Shared password of the fictional demo accounts | Random text in `.env` | `backend/.env`; only a bcrypt hash in the database | Developer, demo users | Change in `.env`, then `php artisan migrate:fresh --seed` | Same as rotation; all tokens are revoked by the reseed |
| Access tokens | Prove a signed-in user | Sanctum at sign-in | Browser memory; SHA-256 hash in the database | The signed-in user | Expire after 60 minutes | Sign out (deletes it), or delete rows in `personal_access_tokens` |

## Rules

- Secrets live only in `.env` or `certs/`, both git-ignored. `.env.example` holds placeholders.
- Secrets never appear in logs, screenshots, evidence or the Flutter build. The secret scan (W11) checks tracked files, the log and the evidence folder.
- Development and production secrets are separate. These are development keys for fictional data. A real deployment generates its own and keeps them in the host's secret store.
- A suspected leak is handled by rotation, not by deleting the evidence of the leak.

**Limitation:** keys are plain values in a file on one laptop. There is no hardware key store or automatic rotation, and the gateway's previous key list must be edited by hand.
